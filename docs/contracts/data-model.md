# BrandGuard AI — Database Contract v1.1

**Status:** Proposed reconciled contract for team review  
**Applies to:** PostgreSQL, SQLAlchemy 2.x, Alembic, backend persistence and analysis-result persistence

This document is the canonical database contract for implementation. It aligns the shared API and analysis-result contracts with the approved Backend Architecture and Backend Detailed Design. If a requirement or field is not specified here or in the other approved contracts, do not silently invent it; agree the decision with the affected team members and update the contract first.

## 1. Canonical decisions and naming reconciliation

The following names are canonical across the database implementation. These choices resolve different names used in earlier drafts and should be used by models, migrations, repositories, tests and API/service integration.

| Concern | Canonical decision | Reconciliation |
|---|---|---|
| Organisation membership table | `organization_memberships` | Use the explicit name in the backend detailed design; this replaces `memberships` from the earlier data-model draft. |
| Brand rule storage | `brand_rules` + `brand_rule_versions` | Keep the shared contract's separate parent/version tables. Version-specific rule text and approvals live in `brand_rule_versions`; do not collapse versions into one mutable rule row. |
| Approved fact storage | `brand_facts` + `brand_fact_versions` | Keep the shared contract's separate parent/version tables. `approved_facts` in the detailed design means the approved fact records retrieved by services, not a separate table. Approval status lives on a fact version. |
| Notification storage | `notifications` | Use the shared contract's table name and API-facing in-app notification concept; do not create a second `notification_events` table for the same records. |
| Analysis-job deduplication key | `idempotency_key` | Use this name consistently; it fulfils the dedupe-key requirement described in the detailed design. |
| Finding classification | `result` | Use the analysis-result contract values (`conflict`, `unsupported`, `inconclusive`, `check_unavailable`). The older detailed-design term `certainty` is not a separate database column. |
| Finding-to-job foreign key | `analysis_job_id` | Use the shared data-model contract name rather than `job_id`. |
| Job completion timestamp | `completed_at` | Use this name consistently in storage and API mapping; it represents the `finished_at` concept in the detailed-design table. |

The API contract (`docs/contracts/api-v1.md`) and analysis result contract (`docs/contracts/analysis-result.md`) remain authoritative for routes, request/response fields, job/submission statuses, and finding payload semantics. This document governs relational storage names and integrity rules.

## 2. General database conventions

- Database: PostgreSQL.
- ORM: SQLAlchemy 2.x using the declarative mapping pattern.
- Schema migrations: Alembic. Schema changes must be represented by reviewed, committed migrations; do not hand-edit an environment's database schema.
- Primary keys: UUIDs, generated by the application or database consistently across the project.
- Timestamps: timezone-aware timestamps stored in UTC (`TIMESTAMPTZ` in PostgreSQL).
- Identifiers and field names in the database contract use `snake_case`.
- Use foreign keys, uniqueness constraints, indexes and constrained values where specified below.
- Every organisation-owned record must be associated with an `organization_id` directly or through an explicitly defined parent relationship. Every tenant-specific repository operation must require trusted organisation context.
- The organisation scope must come from authenticated server-side actor context, never from an untrusted request-body `organization_id`.
- Database access belongs in the infrastructure/data-access layer. Routes and domain rules must not embed SQL queries. Application services use repository interfaces and coordinate transaction boundaries.
- Store structured records, extracted text needed for review, hashes, and protected file references in PostgreSQL. Keep original uploaded file bytes and brand-asset bytes in private file storage; do not store them in public frontend assets.
- Passwords must never be stored in plaintext. Persist only the secure password hash.
- JSON-valued structured fields should use PostgreSQL `JSONB` where suitable.

## 3. Entities and fields

Field types below are logical requirements. Choose concrete SQLAlchemy/PostgreSQL types consistently during model implementation. `id` is the UUID primary key unless otherwise stated. Foreign-key targets and nullability must follow the relationships and optionality specified here.

### 3.1 `organizations`

| Field | Requirement |
|---|---|
| `id` | UUID primary key |
| `name` | Required organisation name |
| `created_at` | Required UTC timestamp |

### 3.2 `users`

| Field | Requirement |
|---|---|
| `id` | UUID primary key |
| `full_name` | Required full name |
| `email` | Required, normalized email; unique after normalization |
| `password_hash` | Required secure password hash; never plaintext |
| `is_active` | Required account-active flag |
| `created_at` | Required UTC timestamp |
| `updated_at` | Required UTC timestamp; updated when the user record changes |

Use the agreed maintained password-hashing library from the backend security design (Argon2 via a maintained Python library). Authentication implementation remains in the identity/security workstream; this contract specifies persisted identity fields.

### 3.3 `organization_memberships`

| Field | Requirement |
|---|---|
| `id` | UUID primary key |
| `organization_id` | Required FK to `organizations.id` |
| `user_id` | Required FK to `users.id` |
| `role` | Required role: `admin`, `creator`, or `reviewer` |
| `created_at` | Required UTC timestamp |

Enforce `UNIQUE (organization_id, user_id)`. A user may belong to multiple organisations, but may have only one membership row per organisation. Permission checks must use trusted membership/actor context.

### 3.4 `brand_rules`

This is the parent record for a logical brand rule. Version-specific content and approval state belong in `brand_rule_versions`.

| Field | Requirement |
|---|---|
| `id` | UUID primary key |
| `organization_id` | Required FK to `organizations.id` |
| `title` | Required display title for the rule |
| `created_by` | Required FK to `users.id` for the creator |
| `created_at` | Required UTC timestamp |

### 3.5 `brand_rule_versions`

| Field | Requirement |
|---|---|
| `id` | UUID primary key |
| `organization_id` | Required tenant scope; must match the parent rule's organisation |
| `rule_id` | Required FK to `brand_rules.id` |
| `version_number` | Required positive version number |
| `category` | Required category: `tone`, `terminology`, `messaging`, or `other` (the contract may later add agreed categories) |
| `description` | Optional explanatory description |
| `rule_text` | Required rule content |
| `severity` | Required value: `info`, `low`, `medium`, or `high` |
| `status` | Required value: `draft`, `approved`, or `archived` |
| `created_by` | Required FK to `users.id` |
| `approved_by` | Nullable FK to `users.id` until approved |
| `approved_at` | Nullable UTC timestamp until approved |
| `effective_from` | Nullable UTC timestamp for the effective start time, if specified |
| `created_at` | Required UTC timestamp |

Enforce `UNIQUE (rule_id, version_number)`. An approved version must not be silently overwritten. A change to an approved rule creates a new version and preserves any version referenced by findings.

A draft version may be updated only while it is the latest version for the rule and remains in `draft` status. Updating a draft changes that draft version's fields without creating another version. An approved or archived version must not be edited; changes after approval require creating a new draft version. The parent rule title remains on `brand_rules`, as defined in this data model.

### 3.6 `brand_facts`

| Field | Requirement |

### 3.7 `brand_fact_versions`

| Field | Requirement |
|---|---|
| `id` | UUID primary key |
| `organization_id` | Required tenant scope; must match the parent fact's organisation |
| `fact_id` | Required FK to `brand_facts.id` |
| `version_number` | Required positive version number |
| `fact_text` | Required fact statement/content |
| `source_url` | Nullable URL for the source/reference |
| `status` | Required value: `draft`, `approved`, or `archived` |
| `effective_from` | Nullable UTC timestamp for the effective start time, if specified |
| `expires_at` | Nullable UTC timestamp after which the fact is no longer valid, if specified |
| `created_by` | Required FK to `users.id` |
| `approved_by` | Nullable FK to `users.id` until approved |
| `approved_at` | Nullable UTC timestamp until approved |

Enforce `UNIQUE (fact_id, version_number)`. Unapproved facts must never be treated as authoritative approved evidence. Findings must retain references to the exact fact version used.

### 3.8 `brand_assets`

The database stores metadata and a private storage reference, not the file bytes.

| Field | Requirement |
|---|---|
| `id` | UUID primary key |
| `organization_id` | Required FK to `organizations.id` |
| `name` | Required asset name |
| `asset_type` | Required asset-type label |

| `media_type` | Required media/MIME type |
| `size_bytes` | Required non-negative size in bytes |
| `checksum_sha256` | Required SHA-256 checksum of the stored original |
| `status` | Required controlled approval/lifecycle status; the exact asset-status values must be confirmed before implementing the enum/check constraint because the supplied contracts do not enumerate them |
| `metadata` | Optional structured metadata (`JSONB` where appropriate) |
| `created_by` | Required FK to `users.id` |
| `approved_by` | Nullable FK to `users.id` until approved |
| `approved_at` | Nullable UTC timestamp until approved |
| `created_at` | Required UTC timestamp |

File validation (extension, MIME type, size and file signature) and private storage are application/storage-adapter responsibilities. Do not expose raw storage keys to unauthorised clients. The current contract does not define a separate asset-version table; do not invent one without an agreed contract change.

### 3.9 `submissions`

This is the parent content item. Its current status and current version number are stored here.

| Field | Requirement |
|---|---|
| `id` | UUID primary key |
| `organization_id` | Required FK to `organizations.id` |
| `title` | Required submission title |
| `status` | Required submission status as defined in Section 4.5 |
| `current_version_number` | Required positive version number of the current version |
| `created_by` | Required FK to `users.id` |
| `created_at` | Required UTC timestamp |
| `updated_at` | Required UTC timestamp; updated when submission workflow state changes |

### 3.10 `submission_versions`

Each version is immutable after creation. A revision creates a new row; it must not overwrite the original text, uploaded-file reference or hash.

| Field | Requirement |
|---|---|
| `id` | UUID primary key |
| `organization_id` | Required tenant scope; must match the parent submission's organisation |
| `submission_id` | Required FK to `submissions.id` |
| `version_number` | Required positive version number |
| `source_type` | Required value: `text` or `file` |
| `original_text` | Required for text submissions; nullable for file-only submission when content is represented by the original file |
| `storage_key` | Nullable private storage key; required for file submissions |
| `original_filename` | Nullable original filename for file submissions |
| `media_type` | Nullable content media type where applicable |
| `sha256` | Required content hash of the submitted original |
| `extracted_text` | Nullable extracted/normalised text for analysis and review |
| `created_by` | Required FK to `users.id` |
| `created_at` | Required UTC timestamp |

Enforce `UNIQUE (submission_id, version_number)`. Preserve the original private file and/or submitted text. A finding and an analysis job must point to the exact immutable submission version they use.

### 3.11 `analysis_jobs`

| Field | Requirement |
|---|---|
| `id` | UUID primary key |
| `organization_id` | Required tenant scope; must match the submission version's organisation |
| `submission_version_id` | Required FK to `submission_versions.id` |
| `status` | Required job status as defined in Section 4.6 |
| `idempotency_key` | Required key for safe job creation/retry and duplicate prevention |
| `requested_checks` | Optional structured list/configuration of requested checks (`JSONB` where appropriate) |
| `attempts` | Required non-negative retry/attempt count; incremented atomically for each successful claim |
| `started_at` | Nullable UTC timestamp recording the first-ever processing start; preserved across retries |
| `completed_at` | Nullable UTC timestamp when the job reaches a terminal completed/partial/failed outcome |
| `error_code` | Nullable safe machine-readable failure code |
| `error_message` | Nullable user-safe failure detail; must not include stack traces or secrets |
| `created_at` | Required UTC timestamp |
| `updated_at` | Required UTC timestamp; refreshed on job state changes and successful claims; while processing, it is the available staleness baseline unless a dedicated heartbeat/attempt timestamp is introduced |

Enforce uniqueness of `idempotency_key` within the intended organisation/job scope (canonical constraint: `UNIQUE (organization_id, idempotency_key)`). A submission version can have multiple jobs over time when a deliberately distinct analysis is requested; retries of the same logical job must reuse the idempotency key and must not duplicate persisted findings.

### 3.12 `findings`

Persist findings in the shared analysis-result shape. Use a UUID `id` internally; the API may serialise it as the finding's `id` field without changing the database key.

| Field | Requirement |
|---|---|
| `id` | UUID primary key |
| `organization_id` | Required tenant scope; must match the job and submission version |
| `analysis_job_id` | Required FK to `analysis_jobs.id` |
| `submission_version_id` | Required FK to `submission_versions.id` |
| `category` | Required value as defined in Section 4.7 |
| `severity` | Required value: `info`, `low`, `medium`, or `high` |
| `result` | Required value as defined in Section 4.8 |
| `explanation` | Required human-readable explanation of the finding/uncertainty |
| `evidence` | Optional structured evidence object (`JSONB`) following `analysis-result.md` |
| `source_rule_version_id` | Nullable FK to the exact `brand_rule_versions.id` used |
| `source_fact_version_id` | Nullable FK to the exact `brand_fact_versions.id` used |
| `location` | Nullable structured text range or normalised image bounding box (`JSONB`) |
| `suggested_correction` | Nullable advisory correction; never overwrites original content |
| `detection_method` | Required value as defined in Section 4.9 |
| `requires_human_review` | Required boolean from the analysis-result contract |
| `finding_fingerprint` | Required stable fingerprint used to identify duplicate logical findings within one job |
| `created_at` | Required UTC timestamp |

Enforce `UNIQUE (analysis_job_id, finding_fingerprint)` to prevent duplicate findings for a logical result in the same job. A finding must reference the exact submission version analysed. Its source rule/fact version references are nullable only when not applicable. Before persistence, validate that the job, submission version and any referenced rule/fact versions belong to the same organisation. Do not reference a mutable “latest rule” or “latest fact” in historical findings.

## 5. Required relationships

- One organisation owns many memberships, brand rules, brand facts, brand assets and submissions.
- Users may have memberships in multiple organisations. A membership connects one user to one organisation and grants one role.
- The membership repository may list all memberships for a given user to support authentication and organisation-selection flows. This lookup does not itself select the active organisation. Because the login contract returns one organisation and one role, the API, database and frontend owners must agree on the selection behavior before the login service implements it. Do not infer an active organisation from repository result ordering.
- One brand rule has many immutable rule versions.
- One brand fact has many immutable fact versions.
- One submission has many immutable submission versions.
- One submission version may have multiple analysis jobs over time.
- One analysis job belongs to one exact submission version and has many findings.
- Each finding belongs to one analysis job and one exact submission version; it can reference zero or one rule version and zero or one fact version.
- One submission can have multiple review actions over time; every action refers to the specific version reviewed.
- Audit events and notifications are organisation-scoped; each has an actor/recipient reference where applicable.

## 6. Integrity, isolation and lifecycle requirements

1. Enforce all specified primary keys, foreign keys, uniqueness constraints and constrained values.
2. Add indexes for frequently filtered tenant, submission, status, job, and foreign-key fields. Index choices should be documented in the model/migration implementation.
3. Make every tenant-specific repository method require a trusted organisation identifier/context. Apply organisation scope to reads and writes, including worker operations.
4. Validate that referenced rule/fact versions belong to the same organisation as the submission being analysed. Use composite foreign keys where practical, plus repository/service validation and tests.
5. Use database transactions for related writes such as version creation, job-state transitions, finding persistence and associated audit/notification records.
6. Preserve original submission text/files. A suggested correction or edit never silently overwrites an original; edits create a new immutable submission version.
7. Do not delete approved rule/fact versions still referenced by findings. Preserve the historical references needed to explain previously generated findings.
8. Retries must be idempotent. A retry must not duplicate jobs for the same logical request or findings within the same analysis job, and must not falsely mark partial/failed work as successful.
9. Keep audit data append-only for normal application paths. Retention/deletion must follow the approved data-lifecycle policy and account for related private files and references.
10. Store uploaded files under generated private keys; validate extension, declared media type, size and file signature before processing. Do not expose storage keys or sensitive internal paths in responses.
11. Do not log passwords, access tokens, secrets, complete confidential uploads or unnecessary raw submitted content. Use request/job identifiers for diagnosis.
12. Do not automatically approve content based on analysis findings. Findings are advisory; an authorised human reviewer makes final approval/rejection decisions.

## 7. Repository contract and coordination

Repositories implement database operations and keep SQLAlchemy/database details out of business rules. Each tenant-specific repository method must require the trusted organisation scope explicitly.

The initial repository interfaces are expected to cover:

- users and organisation memberships;
- brand rules and rule versions;
- approved facts and fact versions;
- brand assets;
- submissions and submission versions;
- analysis jobs;
- findings;
- review actions;
- notifications and audit events where required by application services.

Before dependent implementation begins, Girish (database/persistence), Bhumika (API/security/workflow) and Anusha (analysis worker/findings) must agree on the minimum repository method signatures, transaction boundaries and job/finding persistence interface. Tanishqa consumes only the API contract; the frontend never connects directly to this database.

## 8. Migration and testing requirements

- The initial schema must be created through an Alembic migration and committed with the model changes.
- Review generated migration operations before applying them. Do not treat autogenerated migrations as correct without inspection.
- Tests must cover at minimum: model/table registration; foreign-key relationships; normalised unique user email; unique organisation/user membership; unique rule/fact version numbers; unique submission/version number; job idempotency constraint; finding fingerprint uniqueness per job; tenant isolation; exact source-version references; immutable-version behaviour at service/repository level; transaction rollback; and duplicate-finding prevention on retries.
- Use synthetic test/demo data only. Never commit credentials, real customer data or production uploads.
- Add a reproducible local setup/run procedure for PostgreSQL and migrations before relying on database integration tests.

## 9. Contract change procedure

Before changing a table name, field, relationship, status, finding shape or repository interface:

1. Explain the proposed change and its reason to the affected owners.
2. Agree the change with the relevant database, API and analysis owners.
3. Update this document and any affected API/analysis contracts in the same coordinated change.
4. Update models, migrations, repositories, dependent services and tests.
5. Commit the documentation/code change and notify all team members before building further on the changed interface.

No implementation should rely on a silent interpretation of conflicting or unspecified fields. In particular, freeze the allowed `brand_assets.status` values before implementing that constraint.
